## 1. 만들려는 것

macOS 메뉴 막대 오른쪽에 있는 앱과 시스템 항목을 **별도의 일반 앱 창에서 찾아 사용**하는 도구다. 특히 MacBook의 노치 때문에 화면에서 가려지는 항목에 접근하는 것이 핵심 목적이다.

사용자는 Finder나 Dock에서 앱을 실행하고, 열린 창에서 원하는 메뉴 막대 항목을 찾은 다음 해당 항목의 메뉴를 열거나 연결된 앱을 연다. 이 앱 자체를 메뉴 막대에 추가하는 방식은 사용하지 않는다.

여기서 말하는 대상은 Wi-Fi, 사운드, 동기화 도구 등 메뉴 막대 오른쪽의 항목이다. 화면 왼쪽의 파일·편집 메뉴나 실행 중인 모든 프로세스를 관리하는 도구는 이번 범위에 포함하지 않는다.

## 2. 사용자 요구와 아직 정하지 않은 것

### 확인된 요구

- 노치 때문에 가려지는 메뉴 막대 항목을 사용할 수 있어야 한다.
- 일반 앱처럼 실행하고 별도 창에서 항목을 확인할 수 있어야 한다.
- 별도 창에서 항목을 선택해 보거나 실행할 수 있어야 한다.
- 제품 자체가 메뉴 막대에 상주하는 구조는 피한다.
- 우선 기획 문서를 작성한다. 구현은 후속 작업으로 진행한다. (2026-11-08 구현 승인됨)
- 앱 테마는 navy & slate로 한다.
- 목록의 앱을 종료할 수 있으면 좋다. 첫 버전은 소유 앱이 확실한 항목에 한해 확인 창을 거친 정상 종료 요청으로만 제공한다(강제 종료 없음).

### 기획상 제안

- 첫 화면은 앱 이름과 항목 이름을 보여주는 검색 가능한 목록으로 만든다.
- 기본 동작은 해당 항목의 원래 메뉴 또는 팝오버를 여는 것으로 한다.
- 연결된 앱을 여는 동작은 메뉴 열기와 구분해서 제공한다.
- 최초에는 수동 새로고침과 앱 활성화 시 갱신으로 시작한다.
- 별도 서버, 계정, 외부 패키지 없이 macOS 기본 기능으로 구현한다.

### 구현 전에 확인할 사항

- 원래 아이콘을 누르는 것과 같은 동작이면 충분한지, 실제 메뉴 내용도 반드시 이 앱 창 안에 표시해야 하는지.
- 노치 뒤 항목이 macOS의 손쉬운 사용 인터페이스에 나타나는지, 나타난 항목을 실제로 열 수 있는지.
- 지원할 macOS 최소 버전과 실제로 검증할 기기 구성.

이 문서의 제안은 확정된 사용자 요구와 구분한다. 특히 원래 메뉴를 여는 방식은 기술 검증을 위한 첫 후보이며, 창 내부에 메뉴를 완전히 재현하는 기능이 구현 가능하다고 전제하지 않는다.

## 3. 핵심 사용 흐름

### 최초 실행

1. Finder 또는 Dock에서 앱을 연다.
2. 일반 창에 앱의 목적과 손쉬운 사용 권한이 필요한 이유를 표시한다.
3. 사용자가 권한 설정 버튼을 누르면 macOS 설정 화면으로 안내한다.
4. 권한을 허용하고 앱으로 돌아오면 권한 상태를 다시 확인하고 항목을 조회한다.
5. 허용하지 않은 경우에도 앱은 종료하거나 반복해서 권한을 요구하지 않고 안내 화면을 유지한다.

### 항목 사용

1. 목록에서 앱 이름 또는 항목 이름으로 검색한다.
2. 원하는 항목의 ‘메뉴 열기’를 선택한다.
3. 대상 앱에 요청을 전달해 실제 메뉴 또는 팝오버를 연다.
4. 요청이 거절되거나 대상 앱이 종료됐다면 이유와 새로고침 방법을 안내한다.

‘메뉴 열기’는 이 앱에서 접근을 시작한다는 뜻이다. 열린 메뉴의 위치와 동작은 대상 앱 및 macOS가 결정하므로, 이 앱 창 안이나 선택한 행 옆에 나타난다고 약속하지 않는다. 이 방식으로 노치 뒤 항목을 실제로 사용할 수 있는지는 별도로 검증한다.

### 연결된 앱 열기

- 실제 소유 앱을 식별할 수 있고 사용자에게 유용한 경우에만 별도 동작으로 제공한다.
- 메뉴 열기를 지원하지 않는다는 이유로 자동으로 앱 열기를 대신 실행하지 않는다.
- 시스템 서비스나 창이 없는 앱에서는 이 동작을 제공하지 않을 수 있다.

## 4. 첫 버전 범위

| 기능 | 동작 | 완료 조건 |
| --- | --- | --- |
| 일반 앱 창 | Finder·Dock에서 실행하고 창을 다시 열 수 있음 | 메뉴 막대 아이콘 없이 접근 가능 |
| 권한 안내 | 손쉬운 사용 권한 상태와 설정 경로 표시 | 거부·허용·실행 중 권한 해제를 구분 |
| 항목 조회 | 접근 가능한 메뉴 막대 항목을 목록으로 표시 | 같은 앱의 여러 항목도 구분 |
| 가려진 항목 접근 | 화면 좌표나 현재 보이는 범위만으로 항목을 제외하지 않음 | 실제 노치 뒤 항목 조회와 사용 검증 |
| 검색 | 앱 이름·항목 이름으로 목록 필터링 | 결과 없음과 발견된 항목 없음 구분 |
| 메뉴 열기 | 대상 항목이 지원하는 손쉬운 사용 동작 실행 | 메뉴가 실제로 열리는지 수동 검증 |
| 앱 열기 | 연결된 앱을 별도 동작으로 열기 | 대상이 확인된 경우만 제공 |
| 앱 종료 | 소유 앱에 정상 종료 요청(확인 창) | 시스템·중첩 helper·소유 앱 불명은 제외, 요청과 실제 종료 구분 |
| 새로고침 | 사용자가 목록을 갱신 | 종료된 앱과 새로 실행된 앱 반영 |
| 오류 안내 | 미지원·응답 지연·종료된 대상 표시 | 앱 정지나 성공으로 오인하는 표시 없음 |

목록에 보이는 항목 수는 **발견한 항목 수**로 표현한다. macOS가 제공하지 않은 항목의 존재까지 알 수 있다는 가정으로 ‘모든 항목’이나 ‘숨겨진 항목 전체’를 표시하지 않는다.

### 이번에 제외할 기능

- 메뉴 막대 아이콘의 위치 변경, 강제 이동, 숨기기 관리.
- 다른 앱의 원래 메뉴 UI를 이 앱 창 안에 완전히 복제하거나 내장하기.
- 모든 설치 앱을 검색·실행하는 범용 런처와 프로세스 모니터. (목록에 나온 소유 앱의 정상 종료 요청은 예외로 포함)
- 즐겨찾기, 전역 단축키, 자동 실행, 백그라운드 상주, 동기화.
- 화면 녹화로 아이콘을 추출하는 기능, 별도 서버, 계정, 분석 수집.
- 첫 검증 단계의 App Store 제출, 자동 업데이트, 배포 자동화.

제외 기능이 핵심 목적 달성에 반드시 필요하다고 검증되면, 완료한 것으로 처리하지 않고 범위를 다시 정한다.

## 5. 화면 구성

### 기본 창

- 상단: 창 제목, 검색 입력, 새로고침 버튼.
- 본문: 항목 목록. 각 행에 소유 앱 아이콘, 앱 이름, 항목 이름, 사용 가능한 동작을 표시한다.
- 하단: 발견한 항목 수와 조회 상태. 필요한 경우 지원 범위 안내를 표시한다.

첫 버전은 원래 메뉴 막대 아이콘의 이미지 복제보다 식별 가능한 앱 이름과 항목 이름을 우선한다. 하나의 앱에 항목이 여러 개 있으면 항목별 이름을 사용하고, 이름이 없는 경우 앱 이름과 번호로 구분한다. 이때 앱 아이콘이 원래 메뉴 막대 아이콘과 같다고 표현하지 않는다.

### 상태별 화면

| 상태 | 표시와 동작 |
| --- | --- |
| 권한 없음 | 필요한 이유, 설정 열기, 권한 다시 확인 |
| 조회 중 | 진행 표시, 중복 조회 방지, 입력·창 이동 가능 |
| 조회 완료 | 항목 목록과 발견한 항목 수 |
| 발견된 항목 없음 | 접근 가능한 항목을 찾지 못했다는 설명과 새로고침 |
| 검색 결과 없음 | 검색어를 바꾸거나 지우도록 안내 |
| 일부 조회 실패 | 발견한 항목은 유지하고 일부 앱의 조회 실패 안내 |
| 실행 실패 | 선택한 항목의 오류 표시와 재조회 방법 안내 |

키보드로 검색과 항목 선택이 가능해야 하고, 버튼과 아이콘에는 VoiceOver로 구분할 수 있는 이름을 붙인다. 시스템 밝은 모드·어두운 모드와 글자 확대에서 읽을 수 있는 기본 UI를 사용한다.

## 6. 기술 접근 후보

네이티브 macOS 앱을 우선 검토한다. 창과 목록은 SwiftUI, 앱 실행·활성화와 수명 주기는 AppKit, 다른 앱의 메뉴 막대 항목 탐색 및 동작 요청은 ApplicationServices의 Accessibility API를 후보로 한다.

| 목적 | 후보 | 확인할 점 |
| --- | --- | --- |
| 실행 중 앱 식별 | `NSWorkspace` | 시스템 항목을 제공하는 프로세스도 조사 대상에 포함 |
| 메뉴 막대 항목 조회 | `AXUIElement`, `kAXExtrasMenuBarAttribute` | OS·앱별 트리 차이와 노치 뒤 항목 노출 여부 |
| 권한 상태 확인 | `AXIsProcessTrustedWithOptions` | 권한 변경 후 재조회와 필요 시 재시작 안내 |
| 항목 실행 | 지원 액션 조회 후 `AXUIElementPerformAction` | `AXPress`·메뉴 표시 지원 여부 및 실제 결과 |
| 연결된 앱 열기 | AppKit의 앱 활성화·열기 기능 | 창 없는 앱 및 시스템 서비스의 동작 차이 |

### 구현 원칙

- 다른 앱의 접근성 UI를 이 앱의 뷰에 직접 붙일 수 있다고 가정하지 않는다.
- 현재 화면에서 보이는 좌표만으로 조회 대상을 제한하지 않는다.
- 모든 앱이 같은 접근성 트리나 실행 액션을 제공한다고 가정하지 않는다.
- 앱 간 통신에는 시간 제한을 두고 UI 스레드를 장시간 막지 않는다.
- 실행 실패나 시간 초과 시 자동으로 여러 번 누르지 않는다. 응답이 늦어도 첫 요청이 실행됐을 수 있다.
- 권한이 없거나 해제되면 접근 작업을 중단하고 현재 상태를 안내한다.
- 권한 설정을 자동 변경하지 않는다. 화면 녹화 권한은 첫 접근 방식에 포함하지 않는다.
- 외부 전송 없이 로컬에서 처리한다.

## 7. 가장 먼저 할 기술 검증

이 제품의 성패는 목록 화면보다 **가려진 항목을 실제로 사용할 수 있느냐**에 달려 있다. 따라서 UI를 본격 구현하기 전에 아래 검증을 먼저 수행한다.

1. 노치가 있는 MacBook에서 실제로 가려진 항목을 준비한다.
2. 보이는 항목과 가려진 항목이 접근성 조회에서 각각 발견되는지 기록한다.
3. 발견한 가려진 항목에 지원되는 실행 액션을 요청한다.
4. 메뉴 또는 팝오버가 열리고 사용자가 내용을 보고 조작할 수 있는지 확인한다.
5. 시스템 항목, 일반 서드파티 메뉴 앱, 자체 팝오버 앱을 나누어 결과를 기록한다.
6. 노치가 없는 외장 모니터를 연결했을 때 조회·실행 대상이 달라지는지 확인한다.

### 검증 결과에 따른 진행

- **조회·사용 모두 가능:** 검증된 범위부터 첫 버전 구현으로 진행한다.
- **조회 가능, 사용 불가:** 단순 목록을 핵심 요구 완료로 처리하지 않는다. 실행 방식이나 창 안에서 접근하는 대안을 조사한다.
- **가려진 항목 조회 불가:** 현재 접근 방식의 한계로 기록한다. 우회 방법의 가능성과 비용을 확인하고 범위를 재검토한다.
- **기기·권한 부족으로 미검증:** 해당 조건을 미검증으로 남긴다. 빌드 성공이나 가짜 데이터 화면만으로 통과시키지 않는다.

## 9. 검증 기준

- Finder 또는 Dock에서 실행하면 일반 창이 열린다. 창을 닫은 뒤 다시 앱을 눌러 접근할 수 있다.
- 이 앱 자체의 메뉴 막대 상태 아이콘을 생성하지 않는다.
- 권한을 거부하거나 실행 중 해제해도 앱이 멈추지 않는다.
- 실제 노치 뒤 항목이 발견되고 사용 가능한지 기기·앱·OS 버전과 함께 기록한다.
- 동일 앱의 여러 항목, 이름 없는 항목, 시스템 항목을 구분해 표시한다.
- 앱 종료와 응답 지연 상황에서 중복 실행 없이 오류를 안내한다.
- 새로고침과 검색 결과가 최신 목록을 반영한다.
- 다중 모니터와 메뉴 막대 자동 숨김 상태를 확인한다.
- 검색·선택·실행의 기본 흐름을 키보드와 VoiceOver로 확인한다.
- 조회·필터링 등 독립적으로 검증할 수 있는 로직에는 작은 자동 검증을 둔다. 실제 다른 앱의 메뉴 열기는 수동 검증 결과를 남긴다.
