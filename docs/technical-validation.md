해석(관찰한 범위에서만):
- **AXPress의 반환값은 메뉴가 열렸는지를 알려 주지 못한다.** 타임아웃이나 -25205에서도 메뉴가 열렸다. 그래서 앱은 이런 결과를 "실행됐을 수 있음(결과 미확인)"으로 표시하고 자동 재시도하지 않는다.
- 노치에 걸친 시험 항목에서도 메뉴는 메뉴 막대 아래(y 40)에 열려 보이는 위치에 나타났다.
- 메뉴 창 확인은 `CGWindowList`로 한 것이며 화면 캡처로 눈으로 확인한 것은 아니다.

## 구현에 반영한 시간 제한

AX 타임아웃은 요소별로 설정되며 자식 요소에 상속되지 않는다. 그래서 요소마다 설정하고, 시스템 전체 타임아웃도 설정했다. 앱 하나의 조회에는 3초 예산을 두며, 첫 "응답 없음"이 관찰되면 그 앱의 추가 조회를 멈추고 부분 실패로 보고한다. 조회 중 권한 해제가 관찰되면 결과를 반영하지 않고 권한 안내 화면으로 전환한다.

## 노치 안쪽 실제 항목 1건 확인 (Tailscale)

감독 지시에 따라 조회에서 발견된 Tailscale 항목 하나에만, 메뉴를 여는 `AXPress`를 정확히 1회 요청했다(22:57).

- 대상: pid 3345 `Tailscale`, 항목 `3345:0`(이름 없음, 지원 액션은 `AXPress`뿐). 직접 토글 액션이라는 근거는 없었다.
- 직전 조회 좌표: x 885–909, y 7–31. 노치 영역(x 790–1010, y 0–38) 안에 **완전히 포함**됨(`notch=true`).
- 호출 결과: 2.01초 후 `noResponse`(타임아웃). 반환 코드는 성공이 아니다.
- 메뉴 창 관찰: 요청 1.0초 뒤에는 Tailscale의 메뉴 창이 없었고, 3.2초 뒤 `CGWindowList`에 layer 101 창(x 874–1265, y 40–317)이 나타났다. 노치 영역 아래쪽(y ≥ 40)이라 노치에 가리지 않는 위치다. 몇 초 뒤에는 창이 없어져 있었다.
- 한계: 메뉴가 화면에 보이는 모습은 **눈으로 확인하지 못했다.** 스크린샷은 메뉴가 나타나기 전(1.0초)과 사라진 뒤에만 찍혔다. 메뉴 창이 생긴 시점과 사라진 시점은 호출 반환과 어떻게 대응하는지 알 수 없다.
- 안전: 메뉴 안의 항목은 누르지 않았고, Escape 등 키 입력도 보내지 않았다. Tailscale 연결·설정·실행 상태는 바꾸지 않았다(검증 후에도 프로세스 실행 중).
- 결론: 노치 안쪽 항목에서도 메뉴 창이 열린다는 증거가 하나 생겼다. 다만 표본이 1건(메뉴 방식)이고 시각 확인이 없어서 "노치 뒤 항목을 사용할 수 있다"로 일반화하지 않는다.

## 권한 "다시 확인"이 반응하지 않던 문제 (진단과 수정)

증상: 사용자가 시스템 설정의 손쉬운 사용에서 앱을 허용했는데도 권한 안내 화면에서 "권한 다시 확인"을 눌러도 화면이 바뀌지 않았다.

진단(읽기 전용, 앱 종료·재빌드·권한 변경 없이):
- 실행 중인 프로세스와 디스크의 번들은 서명(cdhash)과 실행 파일이 같았고, Spotlight 검색과 `/Applications`·`~/Applications` 확인 범위에서 같은 bundle ID의 추가 번들을 발견하지 못했다.
- 시스템 로그(`tccd`)에서 이 앱이 스스로 보낸 접근성 확인은 설정 토글 이후에도 모두 거부(authValue=0)였다. 같은 시각 로그에 "등록된 서명 요건(cdhash)이 실행 중인 빌드와 일치하지 않음"이라는 메시지가 있었고, 등록된 값과 실행 중인 값은 서로 달랐다. 등록된 값은 이전 빌드로 추정되며 로그만으로 어느 빌드인지는 확정하지 못했다.
- 이 항목은 마지막 빌드보다 이전에 처음 기록됐고, 이후 토글은 허용 값만 바꾸고 서명 요건을 갱신하지 못한 것으로 보인다. 같은 번들을 정상 종료 후 다시 실행해도 거부됐다(검수자 확인). 동일 번들 재시작만으로는 해결되지 않았다.
- 앱 쪽에는 "아직 허용되지 않음"을 알려 주는 표시가 없어서, 거부가 계속될 때 화면이 아무 반응이 없는 것처럼 보였다.

수정(허용 판정은 그대로 `AXIsProcessTrusted` 결과를 쓴다. 서명 요건 완화, 권한 초기화, 인증서 설치, 허용 강제는 하지 않았다):
- 미허용 화면에 마지막 확인 시각과 결과("macOS가 아직 이 앱을 허용하지 않았습니다")를 표시한다. 결과가 같아도 시각이 바뀌어 다시 확인했음을 알 수 있다.
- 현재 실행 중인 번들 경로를 선택·복사 가능한 텍스트로 보여 주고 "이 앱 위치 열기"로 Finder에서 선택한다.
- 복구 절차(설정 목록에서 항목 `−` 제거 → 현재 앱을 `+`로 다시 추가 → 다시 확인, 필요 시 재실행)를 앱 화면과 README에 안내한다. 토글이나 재실행만으로 해결된다고 쓰지 않았다.

검증:
- 확인함: `swift test` 8개 통과(확인 결과 문구가 상태와 시각을 반영하는지 포함), 새 번들 서명 검증 통과.
- 확인함: 임시 위치에 복사한 새 빌드를 따로 실행해(등록되지 않은 경로·서명이라 미허용 상태) 권한 안내 화면의 새 문구를 접근성 텍스트로 읽었고, "권한 다시 확인"을 누를 때마다 확인 시각이 바뀌며 "아직 허용하지 않았습니다"가 유지됨을 확인했다. 사용자의 실행 중 앱에는 손대지 않았다.
- 확인함(독립 검수자, 구현자 아님): 최종 번들을 새로 실행해 권한 안내 화면을 확인했다. "다시 확인"을 누르면 확인 시각이 갱신되고(00:02:28 → 00:02:37) 미허용 문구가 유지됐으며, 실제 번들 경로가 표시됐다. "이 앱 위치 열기"로 Finder에서 정확한 MenuBarGather 번들이 선택됐고, navy/slate 가독성, 줄바꿈, 스크롤도 확인했다. 확인 전후 cdhash는 같았다. 검수자는 별도 경로에서 `swift test` 8개 통과도 확인했다.
- 후속 확인(2026-11-09, 독립 검수자): 사용자의 확인 응답 이후 실행 중인 실제 앱에서 권한 안내 대신 항목 32개·조회 앱 78개·일부 조회 실패 2건이 표시되는 것을 스크린샷과 접근성 상태로 확인했다. 설정 조작 자체는 관찰하거나 대신 수행하지 않았다.
- 권한 안내 화면의 시각 확인은 독립 검수자가 스크린샷으로 수행했다. 후속 목록 화면도 별도 디자인 검수의 원본 화면으로 관찰했다.

## 인터페이스 정돈 (2026-11-09, feat/navy-slate-interface)

기존 navy/slate 테마 안에서 화면을 정돈했다. AX 조회, 권한 판정, 종료 안전 로직은 바꾸지 않았다.

- 목록: 평탄한 목록 유지. 기본 행의 "메뉴 열기"는 조용한 글자, 마우스 오버 행은 테두리 버튼, 선택 행만 강조색 채움. 선택 행은 둥근 선택 면과 강조색 선으로 표시하고, 시스템 기본 선택 띠가 겹쳐 그려지지 않게 했다. 앱 열기·앱 종료는 행의 ⋯ 메뉴와 우클릭 메뉴로 옮겼다(종료 확인 창은 그대로). 넓은 창에서는 내용 폭을 760pt로 모았다.
- 하단: 같은 앱·같은 원인의 조회 실패를 개수로 묶어 요약하고 "자세히" 팝오버에 전체 목록을 보여 준다. 팝오버 목록은 행 높이를 고정하고 최대 240pt를 넘으면 스크롤한다.
- 권한 화면: 1단계(권한 요청·시스템 설정 열기), 2단계(권한 다시 확인과 확인 시각·결과), 복구 패널(재등록 방법, 현재 경로, 이 앱 위치 열기).
- 창: 기본 900×640, 최소 560×420. 내용이 툴바 아래로 지나가지 않는 화면에서도 툴바 배경을 같은 색으로 고정했다.

검증:
- 확인함: `swift test` 9개 통과(조회 실패 묶음 테스트 추가). 독립 검수자도 별도 위치에서 9개 통과와 `git diff --check` 통과, 키보드 선택·종료 확인·권한 경로 보존을 코드 검수로 확인했다.
- 확인함(구현자, 디버그 빌드): canonical 앱과 다른 bundle ID의 임시 번들로 화면을 캡처해 확인했다.
  - 대상: 다크·라이트, 목록·권한 화면, 빈 검색, 실패 상세 팝오버, ⋯ 메뉴, 종료 확인 창, 기본·최소 크기
  - 목록 화면은 터미널의 손쉬운 사용 권한을 상속한 실행이다(실제 데이터이나 앱 자체 권한 검증이 아님).
  - 권한 화면은 실제 미허용 상태다.
  - 라이트 모드는 해당 프로세스에만 실행 인자로 지정했고 시스템 설정은 바꾸지 않았다.
- 확인함(저장소 fixture만 대상): 메뉴 열기 1회 → "응답 없음…" 문구와 해당 버튼 비활성. ⋯ → 앱 종료… → 확인 창 → 종료 요청 → fixture가 실제로 종료되고 목록에서 사라짐.
- 독립 시각 검수(검수자, 구현자 아님): 수정 1회 후 **PASS**. 평가 기준 9개(C1~C5, W1~W4)가 모두 8점이다. B01(기본 행 강조와 선택·포커스)·B02(반복 실패 표시)는 해결됐고, 미해결 P0/P1/P2와 확인된 회귀는 없다.
  - W2(키보드): 마우스 없이 검색 → Tab → 방향키로 fixture 행 선택 → 컨텍스트 메뉴 키 → 앱 종료… → 확인 창 → Escape로 취소까지 확인했다. Tab 이동은 ⋯ 버튼을 건너뛰지만 같은 작업을 컨텍스트 메뉴로 키보드에서 할 수 있다. 모든 Mac 키보드 단축키와 VoiceOver 전체 흐름은 확인하지 않았다.
  - W3(다수 실패): 실제 실패 팝오버 코드에 합성 데이터 30그룹을 넣은 QA 실행본에서 01 → 30 → 01 스크롤과 원인·건수·하단 안내 유지를 확인했다. 30그룹은 스크롤 검증용 합성 데이터이며 실제 OS 조회 오류나 TCC 상태의 증거가 아니다.
- canonical 번들: 검수 통과 후 `scripts/build-app.sh`로 한 번 다시 빌드했다. 서명·Info.plist·스크립트 구문 검사를 통과했다. ad-hoc 서명이 새로 바뀌었으므로 실제 사용에는 손쉬운 사용 재등록이 필요할 수 있다. 독립 검수자가 새 release 번들을 정상 실행해 제목·테마·현재 경로·권한 재확인 시각 갱신·Finder 선택과 서명·소스 일치를 확인했다. 최종 스모크 당시에는 미허용이었으며, 사용자 재등록 뒤의 실제 목록 진입은 아래 후속 확인에서 별도로 검증했다. UI-check의 PASS와 최종 앱 자체 권한 검증은 구분한다.
- 미확인: 마우스 오버 상태 캡처, VoiceOver 전체 흐름, 모든 키보드 단축키, 정확한 pt 측정, 스캔 중·발견 항목 없음 화면(코드로만 확인), 외장 모니터.

## 미검증

- 노치 안쪽 항목의 메뉴를 사람이 눈으로 확인하고 조작하는 흐름. Tailscale 이외의 안쪽 항목, 팝오버 방식 항목.
- 노치 없는 외장 모니터, 메뉴 막대 자동 숨김, 다중 모니터.
- 팝오버 방식 상태 항목(시험 항목은 NSMenu 방식만 만들었다).
- 실행 중 권한 해제·재허용·조회 중 해제 흐름. 권한 허용 상태의 실제 목록 표시는 후속 확인했으나 이 예외 흐름 전체를 검증한 것은 아니다.
- 종료 요청 후 대상 앱이 저장 확인 등으로 종료하지 않는 경우(`stillRunning`)와 요청을 받지 않는 경우의 화면(함수 수준 테스트만).
- VoiceOver·키보드 전체 흐름(⋯ 메뉴와 같은 작업의 키보드 접근은 컨텍스트 메뉴 키로 확인됨). 목록·종료 화면의 시각 확인은 인터페이스 정돈 단계에서 디버그 빌드로 수행했다(위 절).
- Dock 아이콘을 직접 눌러 창을 다시 여는 동작(`open`으로 같은 앱을 다시 실행해 확인했다).
- macOS 26.3 이외의 OS.

## 감독 검수 메모

감독 세션이 `build/MenuBarGather.app`의 권한 안내 창 스크린샷으로 navy/slate 렌더링을 확인했고, "권한 요청 / 설정 열기 / 다시 확인" 버튼이 접근성 요소로 노출됨을 확인했다(당시 앱에 손쉬운 사용 권한 없음). 종료 확인 창의 앱 이름·PID·취소/종료 요청 버튼도 감독의 접근성 상태에서 확인했다. 감독은 수정 반영 후 `swift test` 7개 통과, 서명·plist·셸 구문 검사를 다시 확인했다. 목록 화면은 감독이 직접 보지 못했다. 앱 자체의 손쉬운 사용 권한은 사용자에게 허용을 요청한 상태이며, 허용 후의 실행 확인은 아직 기록하지 않았다.
